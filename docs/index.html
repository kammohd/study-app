Architecture, systems and code

How AI Study is built

A phone-first study app, from a one-page prototype to an invite-only service with its own database, API, scheduler and push notifications. Four interactive machines explain the ideas; the code and every command are below.

Written 27 October 2026Source: github.com/kammohd/study-appFigures: Anatomy

Overview

A study app that grew a backend

AI Study is a phone-first study tracker with four learning tracks, weekly goals, AI-written quizzes and coding challenges, and a nudge at the time you chose to study. It started as one HTML page that saved progress to a Google Sheet. Over two days of work it became an invite-only, multi-user service with its own database, API, scheduler and push notifications, all on free tiers and under a hard spending cap.

4learning tracks: Python & AI, DSA, Salesforce Admin, SQL
25API paths on one FastAPI service
13Postgres tables, all with row-level security
64backend tests, none of which touch the network
1,349lines of backend Python, plus 964 lines of tests
2,138lines in the one-file front end, no build step

This page explains how it is built from the outside in. Each major idea has an Anatomy figure: an invented machine whose working is the idea, so you can watch the mechanism instead of reading about it. After the figures come the code, the exact commands that were run, the tests, and an honest list of what went wrong.

1 · The big picture

One bench, five stations

Everything in the system is one of five things, and a request only ever travels between two of them at a time.

StationWhat it really isWhere it livesWhy it is a separate piece
The app (tablet on a dock)A single installable web page: index.html, sw.js, manifest.json, and JSON files for the tracks.GitHub Pages, served as static filesIt holds no secrets and does no trust decisions. Anyone can read all of its code.
The API (bay of four trays)A FastAPI service. It checks who is calling, applies the rules, and is the only code that holds secrets.Google Cloud Run, one instance maximumAnything that costs money, or needs a secret, has to run where the browser cannot see it.
The database (chest of drawers)Postgres with Google sign-in, from Supabase. ${NUMBERS.tables} tables; every one has row-level security switched on.Supabase (free tier)It enforces who may see which row, so a bug in the API cannot leak another person's data.
The model (lens)Google's Gemini API, called only from the API, with its key held in Secret Manager.Google AI, free tierA swappable supplier. Every answer from it is treated as untrusted until it passes the quality gates.
The scheduler and bell (clock)Cloud Scheduler wakes the API once an hour; the API sends web push through the browser's own push service.Google Cloud Scheduler, then Apple, Google, Mozilla or Microsoft push servicesCloud Run sleeps when idle, so something outside it has to ring the bell on time.

The six steps in the figure

  1. App → API. Opening a topic sends a request carrying your login token (a signed JWT).
  2. API → database. The API checks you are on the invite list, then reads the question bank that everyone shares.
  3. API → model. Only if the bank is empty does it ask Gemini for a batch, and the batch is checked before it is kept.
  4. Reply. Verified questions are stored, so the next person gets them for free, and served back.
  5. Scheduler → API. Every hour a timed call asks the API who is due a nudge.
  6. API → bell. For each person who is due at their own local 8pm or 9pm, the API sends web push to their devices.

3 · The app

One file, no build step

The front end is deliberately plain: index.html holds the markup, the styles and about two thousand lines of JavaScript. There is no framework, no bundler and nothing to install, which is why it deploys by simply pushing to GitHub. The pieces around it are small: sw.js (the service worker), manifest.json (so it installs like an app), and one JSON file per track in content/.

PartWhat it does
TabsToday (what is due, the quote, goals so far), Plan (this week's goals per track and the next step in each), Library (every topic in every track), Me (account, notifications, admin screens).
TracksPython & AI is a 16-week plan written into the page. DSA, Salesforce Admin and SQL are loaded from JSON: each topic has videos, a vetted summary or the official exam objectives, and exercises with hidden tests.
GoalsA weekly target per track (defaults: Python 6, DSA 3, Salesforce 3, SQL 2) counted from the dates on your ticks. The week resets every Monday, so a missed week never piles up as debt.
Python in the browserExercises run through Pyodide (Python compiled to WebAssembly), cached by the service worker so practice works offline. An AI-written challenge is run against its own tests before you ever see it; a broken one is reported and retired.
Signed outA guest sees only the gate: Sign in with Google, Request an invite, and a link to this page. No tab, topic or quiz is reachable. Between visits the signed-in state is cached so an invited person still gets in offline.

How the page talks to the backend

All server calls go through one helper. It takes the current login token from Supabase's session, sends it as a bearer token, and turns any error into a readable message. A second flag, aiOn(), decides whether AI buttons appear at all.

Progress that survives being offline

A tick is saved locally first and queued for upload (cq). pullTicks() sends the queue, then replaces the local state with the cloud's, but only if nothing is waiting to upload, so an offline tick is never overwritten.

Teaching the server what to nudge about

The server writes the nudge, but only the page knows the curriculum. So after every change the page sends a one-line summary of what is still behind, plus the device's timezone. An empty summary means every goal is met, and the server stays silent.

The life of one request

  1. CORS. Only the Pages origin may call from a browser.
  2. Who are you? The token's signature, expiry, audience and issuer are checked against Supabase's published public keys. Nothing is looked up in a database to log you in.
  3. Are you invited? Features that cost money check the invite list, using the backend's own key.
  4. The handler runs. Your own data is read and written with your token, so the database applies its own rules on top.

Two ways to talk to the database

db.py exposes the same operations in two flavours. Methods called get, upsert, delete forward the user's token, so row-level security applies. Methods called admin_get, admin_upsert use the secret key, which bypasses row-level security, and are used only for things that belong to the system: the invite list, quotas, the shared banks. Choosing the method is therefore a security decision, made at every call site.

5 · Data and access

Who gets in, and which drawer opens

Two separate questions are answered in two separate places, and they are deliberately not the same check.

Gate: invite-only sign-up

A guest cannot see anything but a gate: a sign-in button and a form to request an invite. Anyone can press "Sign in with Google", but a database trigger runs before a new account is created and refuses any email that is not on the allowed_emails list. Because the rule lives on the table that holds accounts, it covers every sign-in route at once: Google, a magic link, even an anonymous login (which has no email at all, so it is refused too).

Not invited? Ask

One step in Figure 2 shows the other way in. A stranger posts a request into a box instead of showing a card; an admin approves it, and the ledger gains a row. In the app that is a public form that calls POST /invite-requests. It is the one place a stranger can write to the database, so it is built to be boring and hard to abuse:

  • It always says the same thing. A new request, a repeat, and an email that is already invited all return {"ok": true}, so the form cannot be used to find out who has an invite.
  • It does not keep the network address. It keeps a keyed hash of it, only to count requests: five per network per day, and a ceiling on how many can be waiting at once.
  • It ignores bots. A hidden field that a person never fills in; a bot that fills it gets a cheerful "ok" and nothing is stored.
  • It asks the admin, in two ways. The Me tab gets a badge and an "Invite requests" card, and every device an admin registered receives a push notification. Failing to notify never fails the request.
  • Approving is the only thing that grants access. It adds the email to the invite list; the requester then signs in with Google and the trigger lets them through. Decided requests are deleted after 90 days by the hourly job.
Honest limit
The request form does not prove you own the email. That is deliberate: the admin vets each one, and approving only lets that address sign in with Google, which does prove it. Everything the page protects is behind that login; the track and plan content is plain files in a public repository, so it is not hidden from someone who reads the repo.

Drawers: row-level security

Once you are in, every table that holds personal data carries a policy that says "you may only touch rows whose user_id is yours". The API forwards your own token to the database, so the database itself applies the rule. A bug in the API that forgot to filter by user would still return nothing for other people's rows.

Why
The policy says (select auth.uid()) instead of auth.uid(). Postgres then evaluates it once per query rather than once per row, which matters as tables grow.

Two keys, two jobs

KeyWhere it livesWhat it can do
Publishable keyIn the page, in public. That is by design.Only what row-level security allows for the signed-in person.
Secret keyEnvironment of the Cloud Run service only.Everything, bypassing row-level security. Used for the invite list, quotas, the shared banks and the hourly job.

Login tokens are signed with an ES256 key pair. The backend downloads Supabase's public keys once and verifies each token's signature, expiry, audience and issuer locally, so there is no shared secret to leak and no per-request call to the auth server.

Watch out
Every new table gets enable row level security in the same script that creates it. A table without it is readable by anyone holding the public key, which is the single easiest way to leak data in this kind of stack. This was verified by hand against the live database: queried with the public key, the closed tables return an empty list.

6 · The AI pipeline

Never trust a model, inspect it

A language model will happily write a confident question with a wrong answer. So nothing it writes reaches a learner until it has been through gates the model cannot argue with. The figure follows four questions down the line; each dies, or lives, at a different gate.

Shared bank, personal progress

Generated questions go into one bank that everyone shares, so the second person to open a topic gets their questions instantly and at no cost. What each person has done with a question (seen, right, needs another go) lives in a separate per-user table. A question you answered right never returns for you, but is still fresh for everyone else.

The four gates

  1. Shape. A real question of reasonable length, exactly four distinct options, and an integer answer index from 0 to 3.
  2. Evidence. For topics written from a source text (DSA, SQL), the model must quote the passage that proves the answer, and at least 80% of that quote's word-triples must appear in the source. An invented quotation fails. Salesforce questions are written from the official exam objectives instead: each question must name the numbered objective it tests, and that objective line becomes its evidence.
  3. A blind second opinion. A second call answers every question without seeing the claimed answer. A question survives only if the second call picks the same option and says it is sure.
  4. Shuffle. Models love putting the right answer first, so the options are shuffled and the answer index follows.

If the blind check cannot be read at all (the model returned something that is not JSON), nothing is trusted: the batch is discarded. If a whole batch is rejected, the server writes one more batch under the same quota charge, and the page retries once more. That is why a topic opened for the very first time sometimes takes a moment longer.

The model client and the cost ceiling

The model client asks for JSON, turns off the model's hidden "thinking" for speed, and falls back to a lighter model when the first is rate limited. It never lets a missing key or a busy model crash a request: hints and grading degrade to a friendly message.

Spends one AI callFree
Generating a question batch; generating a challenge batch; a hint; a grade.Serving a banked question or challenge; recording an answer; the daily quote; the hourly nudge.

Code the model wrote is run before you see it

A server cannot safely run arbitrary Python, so challenges are checked in your browser: the page runs the model's reference solution against the model's own tests in Pyodide, and only shows the challenge if they pass. A challenge that fails is reported back and retired for everyone.

Honest limit
The model can still be subtly wrong in ways no gate catches, for example a true but unhelpful question. The gates make wrong answers rare; they do not make them impossible. That is why every question can be answered, and why a wrong one costs a learner a minute, not a certificate.

7 · Notifications

A bell that rings at your own 8pm

Cloud Run sleeps when nobody is calling, so something outside it has to wake it. Cloud Scheduler calls POST /internal/nudge once an hour. The API then works out, for every person with a device registered, what time it is where they are, and rings only if it is 20:00 to 20:59 (the kickoff) or 21:00 to 21:59 (a follow-up, if they have not studied).

Toggle the three switches under Figure 4 to see each rule: already studied silences only the 9pm reminder, every goal met and Sunday silence everything.

The hourly job, in full

How a push gets to a phone

  1. Subscribe. The page asks the browser for permission and gets a subscription: an address at Apple's, Google's, Mozilla's or Microsoft's push service, plus encryption keys. It sends that to /push/subscribe.
  2. Sign. To send, the API proves who it is with a VAPID key pair. The public half is in the page; the private half lives only in Secret Manager.
  3. Deliver. The push service wakes the device, and the service worker (sw.js) shows the notification even if the app is closed.
  4. Clean up. If a push service says a device is gone (404 or 410), the API deletes that registration so it stops trying.
Watch out
That host check is not decoration. The subscription address is a URL the browser supplied, so without the check a signed-in user could make the server send requests to any address, including internal ones such as the cloud metadata server. Letting only the four push services through closes that hole (it is called server-side request forgery).

Things worth knowing

  • The job wakes on the hour. In a zone with a half-hour offset such as India (UTC+5:30), the scheduler runs at 15:00 UTC, which is 20:30 there, still inside the 20:00 hour. So the "8pm" nudge arrives at 8:30pm. A per-minute job would fix it, at the price of 60 times more calls.
  • No double sends. last_nudge records the day and stage, so a retried job cannot ring twice.
  • The text is written by the fast model from the weekly summary the page sent, with no names in the prompt, and falls back to a plain sentence if the model is busy.
  • The key to the whole feature is a shared secret. The hourly endpoint accepts only a request carrying the right x-cron-token, compared in constant time, and is closed entirely if no token is configured.

8 · The team board

What the administrator can see

The admin's Me tab has a "Team this week" card: every invited person ranked by lessons and topics completed this week, with goals met, study streak, last activity, quiz accuracy, challenges solved and AI calls used today. People who were invited but have never signed in are listed last. The calculation is a set of pure functions with no database in them, which is why it is easy to test.

The rules mirror the app on purpose: the same default goals, a week that starts on Monday, and the same definition of an item done (a Python lesson tick, or a finished DSA, Salesforce or SQL topic). Videos and exercises do not count.

Why
This is the one place where one person's activity is visible to another, so it is admin-only on the server (not just hidden on the screen), shows counts and never answers or code, and is spelled out in the privacy policy. A leaderboard visible to every user was left out on purpose: that would need each person's consent.

The kill switch

A budget alert is only an email unless something acts on it. This function is triggered by the budget's messages and removes the billing account from the project the moment spend reaches the budget. Without billing, Cloud Run, Secret Manager and the scheduler stop; the free static site and the database keep running.

5 · The hourly scheduler

bash
gcloud services enable cloudscheduler.googleapis.com --project=study-app-512819

A one-off: turn on the Scheduler API for the project.

bash
gcloud scheduler jobs create http nudge-hourly --project=study-app-512819 --location=us-central1 \
  --schedule="0 * * * *" --time-zone="UTC" \
  --uri="https://<service-url>/internal/nudge" --http-method=POST \
  --headers="Content-Type=application/json,x-cron-token=$(cat <path-to-token-file>)" --message-body="{}"

Every hour, on the hour, call the nudge endpoint with the shared secret. The token is read from a file so it is never typed. Careful: this command prints the job's headers, token included, so run it in a place where the output is not recorded.

bash
gcloud scheduler jobs update http nudge-hourly --project=study-app-512819 --location=us-central1 \
  --update-headers="Content-Type=application/json,x-cron-token=$(cat <path-to-token-file>)" > /dev/null

Change the token. Pass Content-Type again: an update resets it to application/octet-stream, and the API then answers 422. The redirect keeps the echoed token off the screen.

bash
gcloud scheduler jobs run nudge-hourly --project=study-app-512819 --location=us-central1

Fire the job now instead of waiting for the next hour.

bash
gcloud scheduler jobs describe nudge-hourly --project=study-app-512819 --location=us-central1 --format="yaml(state,lastAttemptTime,status)"

Check it ran: an empty status: {} means the last attempt succeeded. Selecting only these fields avoids printing the headers.

bash
gcloud secrets versions add cron-token --project=study-app-512819 --data-file=<new-token-file>
gcloud scheduler jobs update http nudge-hourly ... --update-headers="Content-Type=application/json,x-cron-token=$(cat <new-token-file>)" > /dev/null
gcloud run services update study-app-api --region=us-central1 --project=study-app-512819 --update-secrets=CRON_TOKEN=cron-token:latest
gcloud secrets versions disable <old-version> --secret=cron-token --project=study-app-512819

Rotating the token, in order: new secret version, new job header, restart the API on it, then disable the old version. Afterwards the old token must answer 401 and the new one 200.

11 · Tests

64 tests, no network

The tests build a throwaway key pair and sign their own login tokens, and replace the database, the model and the push services with small fakes. They run in about a second, so they run every time anything changes. A fake model is told exactly what to say, which makes every quality gate testable: invented evidence, a blind answer that disagrees, an unreadable check.

Test fileTestsWhat it proves
test_api.py10Login tokens: missing, expired, wrong audience and forged ones are all refused. Progress, goals, the invite list, and that only admins reach admin routes.
test_quizgen.py9Every gate on its own: bad shapes, fabricated quotes, disagreeing or unsure checks, an unreadable check, shuffling keeps the right answer right.
test_ai_routes.py11Generate when the bank is empty, serve from it with no model call, wrong answers return until right, a failed batch is retried under one charge, the daily limit, challenges, hints, grading.
test_push.py14Only real push hosts are accepted, the 8pm and 9pm rules across time zones and Sundays, the cron token, no double send, dead devices removed, prompts carry goals and no names.
test_invites.py12A public request needs no login; the address is stored only as a keyed hash; bad emails and the honeypot; identical answers for new, repeat and already-invited; the per-network limit even against a forged header; the queue cap; admin-only decisions; approve adds the email once; admins get a push and a failing push never blocks; un-invited logins get 403 on their data; the 90-day purge.
test_activity.py8Week boundaries, goal overrides, the streak, ranking, admin-only access, and that internal ids are never exposed.
Why
Fakes are only as good as their fidelity, so the live system was also exercised by hand after each deploy: an unauthenticated call must answer 401, the dry run must find the right people, and a forced test nudge must reach a real phone. Two of the problems in the next chapter were found that way, not by a test.

12 · What went wrong

Problems, causes and fixes

None of these was fatal, and every one taught something. They are listed because the next person will hit them too.

What happenedWhyWhat fixed it
The AI topic builder was designed, then dropped.A spike showed Gemini's Google Search grounding is refused on the free tier: every callable Flash model answered 429 with grounding while plain calls worked, and the older 2.5 models are closed to new users.Cancel the feature rather than pay or build on a model being retired. The spike script was a throwaway; the finding is the useful part.
The first question of a new topic failed now and then.A fresh batch can lose every question at the blind check, or the sleeping server is slow on its first request.One automatic retry on the server (same quota charge) and one in the page.
The cron token was printed in a terminal.gcloud scheduler jobs create echoes the job back, headers included.Rotate it at once: new version, new header, restart, disable the old. Now every such command redirects its output.
The scheduler's first run failed with 422.Updating the job's headers reset Content-Type to application/octet-stream, so the API refused the body.Pass Content-Type=application/json on every update, and read the status in the service's own logs, not only in the scheduler's.
A token rotation silently did nothing.Windows Python could not read a /c/... path, so the new token was never generated, and the next four commands re-registered the old one.Check each step's result and stop at the first failure; use the path style the program expects.
A new test file broke an old one.Both set the same environment variable at import time, and the later file won.Set shared variables in one place only.
A fake database dropped test data.Fake attempts had no timestamp, so the 'this week' filter correctly excluded them.Give the fake the same shape as the real table.
The status dot said “synced” and never “cloud synced”.While the old Google Sheet sync still ran beside the new cloud sync, whichever finished last wrote the label.Remove the old sync. The overlap was temporary by design.
Commands pasted into the chat did nothing.Only text typed at the prompt with a leading ! runs as a command; the same text sent as a message is just text.Run each command on its own line from the prompt.
PowerShell refused to run gcloud.Script execution policy blocks the gcloud.ps1 wrapper.Use gcloud.cmd in PowerShell, or run gcloud from a bash-style shell.
Google would not verify the sign-in screen.It could not confirm the site was the owner's, and the app name on the consent screen did not appear on the homepage.Prove ownership with Search Console's HTML-file method and show the app name and policy links on the homepage in plain HTML.
A public repository was blocked by a safety check.Creating a public repo is a public-facing action, and rotating a secret is a write to the secret store; both need explicit permission.Narrow, explicit permission rules for just those commands.

13 · Limits, costs and what is next

Honest limits

  • Half-hour time zones get their nudge half an hour late. The scheduler wakes on the hour, so "8pm" in a UTC+5:30 zone arrives at 8:30pm. Daylight-saving changes are handled because the job uses real time-zone rules, but only at that same hourly grain.
  • The free AI tier is tight. Heavy testing uses up the model's daily quota, and a first look at a topic can cost two model calls. The per-person limit (20 a day) protects the shared allowance.
  • One instance, cold starts. After a quiet spell the first call is slow. That is the price of a hard cost ceiling.
  • Large lists are capped. By default Supabase's REST layer returns at most 1,000 rows per request. Some endpoints ask for more; at invite-only scale it does not matter, and it would need paging if the user count grew.
  • The lock protects the app, not the repository. The tracks, the Python plan and the page itself are plain files in a public repo. A guest cannot use any feature or read anyone's data, but could read those files.
  • The gates make wrong questions rare, not impossible. See chapter 6.
  • Nudges follow the weekly goals the page computes from the device's own state, so a device that has not synced for days can nudge about something already done elsewhere, until it syncs.

Cost

Everything runs on free tiers: GitHub Pages, Supabase, Cloud Run's request-based free allowance, Secret Manager, Cloud Scheduler's free jobs and Gemini's free tier. The backstop is the $10 budget with the kill switch, plus one-instance Cloud Run and the per-person AI limit.

Ideas left on the table

  • An opt-in leaderboard visible to every user (needs each person's consent and a privacy-policy change).
  • An AI topic builder with real sources, if billing is ever enabled for grounding, or built on Wikipedia plus links the user pastes.
  • A per-minute scheduler if exact local times matter more than the number of calls.
  • Paging for the few long lists, and a spaced-repetition review built on the attempts table, which already records everything it would need.
